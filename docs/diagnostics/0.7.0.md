# 0.7.0 诊断报告：进度卡 0 与表2 部分翻译/字号

> 诊断方法遵循 /diagnosing-bugs：先建反馈循环，再定位根因。
> 环境：Zotero 10.0.6（官方安装版）、BabelDOC 0.6.4、PyMuPDF 1.28.2、插件 0.6.0（profile xpi 171,818B）。
> 用户最近一次翻译：Sharafaldin 等 - 2018（CIC-IDS2017 数据集论文），附件 key K9TTV6D5，2026-10-22 02:23–02:25，2 个请求，280 段。

## 1. Bug B：进度一直 0、计时 0、卡在"准备 BabelDOC"

### 反馈循环（已建成并运行）

临时 Zotero profile（G:/ProgramData/zotero-translate-files/ztest/diag-profile）加载诊断插件，复刻 queue.js 的 openProgressWindow / refreshProgress / showProgressWindow / scheduleProgressRefresh 逻辑，每秒刷新并把 DOM 文本写入 Zotero debug 日志。

命令（stdout 重定向到 build/diag/zotero-stdout2.log）：

    "G:/Program Files/Zotero/zotero.exe" -no-remote -profile <diag-profile> -ZoteroDebugText

### 关键输出（原样）

    ZTFPROG itemProgress keys=[]
    ZTFPROG refresh before show done
    ZTFPROG add captured
    ZTFPROG hook: popupWindow captured, unload listener added
    ZTFPROG show returned
    ZTFPROG schedule done active=true timer=16
    ZTFPROG tick 1 active=false dom=正在准备 BabelDOC（已用时 0:00） · 0%（队列中还有 0 篇）
    ZTFPROG tick 2 active=false dom=正在准备 BabelDOC（已用时 0:00） · 0%（队列中还有 0 篇）
    ...（tick 3–6 相同）

### 根因

Zotero 10.0.6 的 ProgressWindow 是异步打开（about:blank -> chrome 文档）。插件在 showProgressWindow 的 add hook 中给 popupWindow 注册的 "unload" 监听，会在窗口加载早期（about:blank 文档卸载）触发一次；回调 entry.onPopupUnload -> stopProgressTimer(entry) 把 active 置 false 并清除 timer。
之后：
- 每秒 tick 的 refreshProgress 因 currentProgress.active=false 直接 return；
- runner 的 ZTF_PROGRESS 事件也因同一检查被丢弃；
- 窗口停在初始文本"正在准备 BabelDOC（已用时 0:00） · 0%"。
这也解释了 0.5.2 及更早版本"一直如此"：同一段 unload hook 逻辑长期存在，只是 0.6.0 的每秒计时让现象更明确。

### 修复方向

- add hook 同时监听 popupWindow 的 "load"，设置 entry.popupLoaded；
- onPopupUnload 仅在 popupLoaded 之后生效（忽略加载早期 about:blank 的 unload）；
- 保留 window.close / closeProgressWindow / stopProgressTimer 既有行为；
- 回归测试：harness 模拟"打开时先早期 unload、后 load"，断言进度文本每秒更新、active 不因早期 unload 停止。

## 2. Bug A：表2 字体变小 + 部分翻译部分不翻译

### 证据 1：产物实测（用户译文副本）

文件：C:/Users/A/Desktop/论文/IDS · 安全告警降噪/01 数据集与评测/Sharafaldin 等 - 2018 - ..._2.pdf（双语，第 5 页 = 0-based 4）。

| 区域 | 文本 | 字号 |
| --- | --- | --- |
| 源表2 单元格 | Days / Labels / Monday Benign / BForce,... | 9.96pt |
| 译文单元格（已翻译） | 暴力破解、SFTP 和 SSH；DoS 和 Hearbleed 攻击；端口扫描（...） | 6.48pt |
| 译文单元格（未翻译） | Monday Benign；slowloris, Slowhttptest, Hulk and GoldenEye；Infiltration Dropbox Download and Cool disk；DDoS LOIT, Botnet ARES,；sO,sA,sW,sR,sL and B) | 9.96pt（保留原文） |

结论：翻译成功的单元格被 BabelDOC 缩到源字号的 65%（9.96 -> 6.48），未翻译的保持 9.96，于是"翻译的字变小、未翻译的没变"，叠加"部分翻译"。

### 证据 2：表体规则（单元红灯，build/diag_rule_loop.py）

    FAIL 'Benign' body -> keep short_value            expected translate
    FAIL 'Monday' body -> keep short_value            expected translate
    FAIL 'Harrison' body -> keep short_value          expected translate
    FAIL 'Network Scans' body -> keep short_value     expected translate
    FAIL 'https://example.org/x' body -> translate    expected keep（4 词规则绕过 URL 判断，回归）
    FAIL meaningful_chinese 'sO、sA、sW、sR、sL 和 B）' -> False   expected True

### 证据 3：日志（GRASRNS3 用户翻译）

- invalid_chinese_fallback 21 次（Q11 回退误伤，包含 sO 枚举、Init Win F.Bytes 等）；
- table_analysis：表 2 uncertain（headers=0）、表 3/4/5 clear；
- body_font_scale_summary：10pt 类 0.95、行距调整 74 段（正文缩放，与表格 0.65 是两套机制）。

### 根因

1. 表体规则按"短值保留"（len(words)<=3 -> keep），与用户期望"表体所有英文都翻译，仅纯标识符/数字/代码保留"冲突；
2. Q11 中文有效性判定要求 >=2 个 CJK 实词，短枚举/混合译文被误判回退；
3. is_identifier 的长句分支先于 URL/代码分支返回 False，URL 被误送译（回归）；
4. 表格单元格字号来自 BabelDOC 排版器 _find_optimal_scale_and_layout/_get_optimal_scale：按单元格 box 自动缩放到放得下（0.65 = 9.96 -> 6.48），不是我们的 0.95 正文缩放。

### 修复方向

- 规则票：表体只保留 identifier/number/URL/code，其余（1–2 词普通英文、含专名整句）送译；Q11 放宽为 >=1 CJK 且非纯数字/标点/回声，且只作用于短值（source 词数 <=3 或长度 <=40），不用于整句；修 URL 回归。
- 字号票（另立；**0.7.0 已封存**，此为历史记录）：最初方案为 patch BabelDOC 表格单元格排版、最小缩放 0.9 并允许单元格增高换行；后续改为严格原边框（不增高、放不下允许溢出），最终随表格翻译封存（ADR 0007）。

## 2.3 修复后在真实 Zotero 的验收（诊断插件 v3）

在 ztest 临时 profile 中用诊断插件复刻修复后的进度逻辑（popupLoaded 门控 + load/unload 监听清理），Zotero 10.0.6 实跑输出：

    ZTFPROG hook: load+unload listeners added
    ZTFPROG schedule done active=true timer=16
    ZTFPROG early unload ignored          <- about:blank 早期 unload 被忽略
    ZTFPROG popup load fired
    ZTFPROG tick 1 active=true dom=模型正在翻译（已用时 0:00） · 15% · 请求 1/6
    ZTFPROG tick 2 active=true dom=模型正在翻译（已用时 0:01） · 30% · 请求 2/6
    ...（tick 3–6 依次 0:02..0:05、45%..90%）
    ZTFPROG closed by window.close, active=false
    ZTFPROG after close active=false timer=null

结论：修复后计时每秒递增、进度百分比随事件推进；真实窗口关闭后 timer 正确停止。Spec 审查提出的"load 不触发"残余风险已排除。
